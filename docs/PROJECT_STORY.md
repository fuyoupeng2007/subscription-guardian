# 🧠 订阅管家的故事 —— A Beginner's Journey

> **项目**：订阅管家 · Subscription Guardian
> **参赛**：Agents for Humans Hackathon（Strands Agents SDK）

---

## ✨ 灵感来源 Inspiration

一开始我根本算不上"会做 AI"。我甚至不知道什么是 **LLM API Key**——参加这个黑客松时，我只知道自己是个被一大堆付费会员包围的普通用户：爱奇艺、腾讯视频、QQ音乐、iCloud、百度网盘……每个都在默默扣钱，我完全记不清自己到底开了多少、有没有重复。

我想要的不是一份"报告"，而是有人能**在后台替我把账算清**：我这个月该交多少钱？

$$ \text{每月总支出} = \sum_{i=1}^{m} p_i $$

然后告诉我哪些钱在浪费、哪些会员其实可以根据我的**爱好**来决定要不要开、以及"我喜欢的这首歌，到底在**哪个会员里**能听"。于是就有了这个"订阅管家"。

## 🎓 我学到了什么 What I learned

### 1. 不要让你的 AI 做算术
我犯过最离谱的一个错：让那个本地小模型自己去"算账"，它居然"算"出了**捏造的涨价**和**虚构的重叠**。从此我有一个铁律：

> **数字永远不该由模型猜，而应由代码算。**

我把整个系统分成两层：

$$ \underbrace{\text{确定性计算层 (analyze)}}_{\text{100% 准确}} \;\longrightarrow\; \underbrace{\text{语言表达层 (LLM)}}_{\text{组织中文/英文}} $$

```text
get_financial_facts 工具  →  把已经算好的准确数字交给模型
模型只负责"怎么讲"，绝不负责"再算一遍"
```

### 2. Strands 的"工具即能力"
Strands 让我第一次理解：**智能体的强，是强在会用工具拿真数据**。我给 agent 接了 5 个工具：

| 工具 | 作用 |
|---|---|
| `get_subscriptions` | 取订阅清单 |
| `get_financial_facts` | 取算好、100% 准确的财务分析 |
| `simulate_cancel` | 模拟取消后省多少 |
| `save_report` | 导出报告 |
| `research_content` | **真联网**查"某歌/剧在哪个平台能听" |

### 3. 本地的意义
用 **Ollama + Qwen2.5** 跑在本地：免费、离线、**数据不出电脑**。代价是模型小、思考慢、偶尔简单——但值得，因为它真正"属于我"。

### 4. 确定性代码 > 看似聪明的模型
推荐/算账都能公式化：

**重叠订阅** —— 同类里保留最贵、取消其余的节省：

$$ \text{重叠节省}_c = \Big(\sum_{j \in S_c} p_j\Big) - \max_{j \in S_c} p_j $$

**全部可省**：

$$ \text{可省合计} = \sum_{c} \text{重叠节省}_c = \sum_{c}\Big(\Big(\textstyle\sum_{j \in S_c} p_j\Big) - \max_{j \in S_c} p_j\Big) $$

**取消模拟（模糊匹配）** —— 只要"名称包含"就命中：

$$ \text{hits} = \{\, j \mid \text{name}_j \subseteq \text{query}_i \vee \text{query}_i \subseteq \text{name}_j \,\} $$

这样**每一个数字都能被复核、可复现**。

## 🛠️ 我是如何构建的 How I built it

### 第 1 步：先跑通一条最朴素的中文 REPL
用 **Strands Agents SDK** + Ollama 本地 Qwen，写了一个在终端回答"我花了多少钱"的命令行。先解决"能不能跑"。

### 第 2 步：把"账"交给确定代码
写一个纯函数 `analyze`：读 `subscriptions.json` → 算出总花费、重叠、涨价、续费、可省金额。agent 只通过工具读取这些**真数**。

### 第 3 步：可交互网页 UI
黑终端对于新手不友好，所以我加了一个极简的 `server.mjs`（原生 Node http，零依赖）+ 一个漂亮的单页 UI：**总览 / 报告 / 真实调研 / 按爱好推荐 / AI对话 / 续费提醒**。

### 第 4 步：真联网调研
做"哪个会员有这首歌"时，我发现真正抓各平台版权既慢又被反爬。于是改用各平台**公开搜索接口**直连，拿"能否搜到"作存在性证据：

```text
searchNetease(q) + searchQQ(q) + searchBilibili(q) → {每平台: 找到没, 匹配度}
```

### 第 5 步：中英双版，独立并行部署
最终把同一套逻辑做成**中文版(:3000)** 和 **英文版(:3100)** 两套**互不依赖、各自运行**的应用，并各配 UI / 终端 / 数据 / 提示词。

### 第 6 步：多智能体
分析员→复核员 两轮流水线：分析员先起草，复核员拿"事实摘要"逐条纠错，避免小模型自己编数字：

$$ \text{最终} = \text{Reviewer}\big(\text{Draft},\ \text{GroundTruth}\big) $$

## 🧗 我遇到的挑战 Challenges

1. **模型幻觉**：本地 3B 模型直接总结数字会编造（例子：把"15→22"的芒果TV说成"腾讯涨到 30"）。
   → 解法：**算账交给代码**，模型只接受"事实摘要"再润色；复核员只认摘要有。

2. **Ollama 挂掉拖垮整个 UI**：服务端一个 chat 报错把整网页进程带崩，点"续费提醒"也卡死。
   → 解法：给全部 API 加 **try/catch**，chat 失败只返回一条友好提示，**绝不崩服务**。

3. **真实版权不可爬**：逐平台爬曲库被登录/反爬/JS 挡。
   → 解法：换**公开搜索接口**当"是否收录"，诚实地在 UI 标注"以平台实际版权为准"。

4. **批处理编码坑**：给 `.bat` 写中文，Windows cmd 用 GBK 读就崩。
   → 解法：启动脚本全英文，程序界面才是中文。

5. **给新手的一课**：早期我一步就问很多问题。后来才明白——**先动手做出能跑的 MVP，再问**。

## 🔚 一句话

这个项目教会我最重要的一句话：**"别让 AI 替你想数字，让 AI 替你做决定"**——把 100% 准确的数字交给模型去组织语言，把真实的兴趣与预算交给模型去推荐，把联网查询交给公开接口。剩下的，交给时间、试错与信心。

**Let the math be exact, and let the agent be smart.**
